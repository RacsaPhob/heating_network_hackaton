# Задания для AI помощников участников

Каждый запрос выполняется в своей копии общего репозитория и своей Git-ветке. Вначале прочитать `README.md`, `docs/DATASET_REVIEW.md`, `docs/CONTRACTS.md`, `contracts/rules.json` и исходное техническое приложение. Не поручать всем помощникам менять весь проект одновременно.

## Участник 1 — интерфейс

> Разработай frontend сервиса подключения зданий к тепловой сети. Работай в frontend/. Предлагаемый стек React + TypeScript и Leaflet; согласуй API с docs/CONTRACTS.md. Первый этап: загрузка небольшого локального GeoJSON для предварительного просмотра, карта со слоями существующих труб/камер/источника/ограничений/точек подключения, карточки объектов, панель диагностики. Учитывай, что в исходном файле нет oks_future, ID числовые, есть restriction_type=oks/railway. Не подменяй неизвестные правила. Затем подключи загрузку на сервер, опрос задач, отображение новых сетей/реконструкции и сравнение summaries. Большие файлы отправляй серверу без JSON.parse в браузере. Различай стоимость строительства, реконструкцию, штраф и итоговую стоимость. На первых шагах допустим явно включаемый синтетический mock по согласованному контракту. Не реализуй расчёты маршрутов в UI и не меняй backend/ или contracts/ самостоятельно. Критерий готовности: пользователь может пройти сценарий загрузки, увидеть ошибки или результат и скачать GeoJSON.

## Участник 2 — данные, API и интеграция

> Развивай backend на Java 11, Spring Boot 2.6.3, PostgreSQL, springdoc-openapi-ui 1.7.0, docker-compose 1.29.2. Вначале реализуй общие DTO и интерфейсы domain/ из docs/CONTRACTS.md и согласуй их с участниками 3 и 4. Затем сделай потоковую загрузку GeoJSON на диск, фоновую проверку обязательных свойств и ссылок, преобразование EPSG:4326 в EPSG:32637, пакетное сохранение и статус набора. Исходный датасет не соответствует схеме: возвращай понятные ошибки, не придумывай upstream/расходы/ОКС. Реализуй API задач, ограниченную очередь, статусы и потоковый экспорт. Не читай 3 ГБ через readTree/readAllBytes/MultipartFile.getBytes. Экспорт строго по разделу 10, одна summary с geometry=null на вариант. Ты отвечаешь за Docker, сборку и ежедневное объединение работ. Критерий первого этапа: полный синтетический набор принимается, исходный неполный набор диагностируется, клиент получает согласованный ответ; данные переживают перезапуск.

## Участник 3 — построение сети

> Реализуй routing/ на Java 11 по общим DTO. Работа ведётся в EPSG:32637, метры. Первый этап: допустимый путь от подключения до нескольких кандидатов врезки с обходом запрещённых полигонов; все кандидаты оцениваются инженерным модулем, не выбирай ближайшую врезку только по расстоянию. Следующий этап: совместные ветки нескольких ОКС, дерево без циклов с одной врезкой на компоненту, камеры в разветвлениях со степенью <=4, рациональная полилиния без ступенек. Специальные проходы выделяй отдельными рёбрами по правилам приложения. Используй ширину пары труб при буферах и повторяй геометрическую проверку после назначения диаметров. Учитывай правило камеры в 10 м, существующие примыкания и запрет пересечения новых линий вне узла. Не зашивай координаты/ID; неизвестный railway не считать свободным проходом или трамваем. Глубину пока не делай. Работай на полностью заданных синтетических примерах, геометрию реального файла используй для исследования. Критерий готовности: CandidateNetwork и диагностика, автоматическая проверка маршрута на другом наборе без ручных правок.

## Участник 4 — инженерные расчёты

> Реализуй engineering/ на Java 11, используя contracts/rules.json и общий domain/. Начни с ручных эталонных тестов суммирования расходов и минимального ДУ, затем лимит непрерывной длины одного диаметра: камера/технический узел его не обнуляют. На существующей сети суммируй дополнительные расходы всех врезок до источника; врезка внутри линии нагружает только часть к источнику, несколько врезок разбивают линию на интервалы. Реконструкцию считай по требуемому ДУ, без коэффициентов глубины/спецпрохода. Для камер используй максимальный итоговый примыкающий ДУ; существующие камеры реконструировать только при использовании для врезки, учитывать один раз. Рассчитай категории стоимости, штрафы и score точно по приложению; пример раздела 10.8 не является числовым эталоном. Ошибки/отсутствующие исходные данные не превращай в ноль. Не принимай решение об увеличении минимального ДУ ради длины без уточнения правила. Критерий готовности: EvaluatedVariant, объяснимая стоимость и тесты двух врезок на одной линии, общего upstream, переполнения ДУ, камеры с большим существующим диаметром и частичного подключения.
