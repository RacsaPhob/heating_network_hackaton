# План для четырёх участников на 14 дней

Один репозиторий, один Java backend с разделёнными пакетами и один frontend. Отдельные микросервисы и четыре разных backend не нужны. Участник 2 отвечает за интеграцию; каждый день собираем общий результат. Интерфейсы согласованы в `CONTRACTS.md` и меняются совместно.

## Владение кодом и результат работы

| Участник | Область | Владеет | Приёмка |
|---|---|---|---|
| 1 | Интерфейс и карта | `frontend/` | Загрузить файл, увидеть слои и диагностику, запустить расчёт, сравнить варианты, скачать результат |
| 2 | API, данные, интеграция | `backend/.../api/`, `ingest/`, `storage/`, конфигурация, Docker | Потоковый импорт, ошибки схемы, БД, очередь задач, статус, экспорт, общий запуск |
| 3 | Геометрия и поиск сети | `backend/.../routing/` | Найти допустимые трассы, выбрать врезки, объединить здания, сформировать дерево, проверить отступы и пересечения |
| 4 | Расчёты и оценка | `backend/.../engineering/` | Расходы, диаметры, длины, реконструкция частей старых линий, камеры, стоимость, score, тестовые примеры |

`contracts/` и пакет `domain/` — общие. Ответственный за слияние участник 2; до изменения уведомить остальных. Участники 3 и 4 согласуют цикл поиска: маршрут -> расчёт диаметров -> повторная геометрическая проверка -> допустимый вариант/новая попытка. Без этого разные модули дадут несовместимые ответы.

## План по дням

| Дни | Участник 1 | Участник 2 | Участник 3 | Участник 4 |
|---|---|---|---|---|
| 1–2 | Карта исходного файла, слои, карточки | Контракты Java, импорт и диагностика; вопросы организаторам | Проекция, пространственный индекс, простые препятствия | Каталог правил, расходы, минимальный диаметр, стоимость |
| 3–4 | Статус расчёта и отображение результата по fixture | Рабочий API на синтетическом полном наборе | Отдельные подключения к нескольким кандидатам врезки | Распространение добавленного расхода к источнику, реконструкция |
| 5–6 | Подключение к реальному API | Первая общая сборка, сохранение/экспорт | Совместные ветки, камеры, устранение пересечений | Лимит длины одного диаметра, расходы общих веток, камеры |
| 7–9 | Сравнение до трёх вариантов, объяснение стоимости | Большие файлы, очередь, перезапуск, ошибки | Специальные проходы, рациональная геометрия, альтернативы | Полная стоимость и score, проверка интервалов реконструкции |
| 10–11 | Ошибки/пустые состояния, удобство демо | Незнакомый набор, нагрузка, Ubuntu/Compose | Исправление кейсов на другом наборе | Независимая проверка валидности и ручные эталоны |
| 12–13 | Презентация и демонстрационный сценарий | Чистое развёртывание, инструкция и документация | Описание алгоритма и ограничений | Таблица расчётов для защиты |
| 14 | Общий резерв, прогон защиты, фиксация версии | Общий резерв | Общий резерв | Общий резерв |

Это целевой график, не гарантия трудоёмкости. Дни 5–6 — обязательный первый сквозной результат, даже на небольшом синтетическом наборе. Не откладывать интеграцию на конец.

## Последовательность готовности

1. M0: у всех одна схема и общие единицы; исходные несоответствия видны, неизвестные правила не подменяются.
2. M1: загрузка -> автоматический допустимый маршрут -> расчёты -> карта -> выгрузка на полном синтетическом примере.
3. M2: все объекты, совместные сети, реконструкция, ограничения, проверка на исправленном конкурсном наборе.
4. M3: варианты, качество маршрутов, большие файлы и стабильность на другом наборе.
5. Глубина — только если обязательная часть стабильно проходит приёмку и остаётся резерв; не выделяем под неё отдельного человека с первого дня.

## Как работать с AI и не сломать интеграцию

- Каждый работает в своей ветке: `feature/ui`, `feature/platform`, `feature/routing`, `feature/engineering`. Ветки создаём после появления общего Git-репозитория.
- В запросе AI указывать свою папку, контракт входа/выхода, конкретный сценарий и критерий готовности.
- Просить небольшую законченную функцию, а не «сделай весь хакатон». Проверять результат на реальном примере.
- Не обновлять Java 11, Spring Boot 2.6.3 и Swagger 1.7.0 по инициативе AI.
- Не менять исходный датасет; синтетические примеры хранить отдельно и явно маркировать.
- Не выдавать мок, прямую линию или непроверенный маршрут за корректный расчёт. UI отображает состояния INVALID/PARTIAL и объяснения.
- Сливать небольшие изменения ежедневно; до слияния прогонять тесты своей логики и общий сценарий.
- Один раз в день 15 минут: что работает в общей сборке, что ждёт другой модуль, какие контракты меняются.

## Минимальные содержательные проверки

- Числа: равенство расхода пропускной способности, превышение максимального ДУ, общий расход двух зданий.
- Длины: камера не обнуляет длину того же диаметра; смена диаметра начинает новый отсчёт.
- Реконструкция: врезка внутри линии, две врезки на одной линии, общий upstream нескольких ветвей, нулевой исходный расход только когда он явно задан.
- Геометрия: узкий проход после увеличения ДУ, угол дороги, пересечение новых линий, замкнутый маршрут, пятый участок камеры.
- Экспорт: одна summary на вариант, обязательные поля, null глубины в 2D, согласованность геометрии/длины/стоимости.
- Эксплуатация: загрузка 3 ГБ без полной копии в heap; экспорт 500 МБ потоком; до 50 пользователей без 50 одновременных тяжёлых расчётов на 16 ГБ.
