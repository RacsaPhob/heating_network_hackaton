# Общие контракты v0.1 — архив проектирования

Этот первоначальный план содержит нереализованные endpoint и устаревшие положения о реконструкции и строковых ID. Текущий API доступен в Swagger; для сдачи ориентироваться на `README.md`, `docs/SUBMISSION.md` и `docs/COMPLIANCE.md`.

Это предложенный внутренний контракт команды. Формат конкурсного входа/выхода определяет техническое приложение, а не этот файл. Планируемые endpoint ниже ещё не реализованы; реализация отмечается отдельно.

## Единицы и модель

- Внешний GeoJSON: долгота, широта EPSG:4326. Внутренние X/Y: метры EPSG:32637. Проекция выполняется один раз при импорте и обратно при экспорте. Не измерять расстояния в градусах.
- ID — строки. ID исходных объектов неизменны в строгом режиме. ID создаваемых объектов уникальны во всём выходном файле, включают вариант.
- Расход — т/ч; ДУ — мм; длина — м; стоимость — рубли. Расход пары труб не удваивается, цена таблицы уже применяется к линейному объекту пары.
- Каталог `contracts/rules.json` общий. Не создавать разные копии таблиц в frontend, routing и engineering.
- Для денежных сумм Java использует BigDecimal. Округление только при представлении; ranking использует неокруглённые значения.
- Прототип хранит нормализованную область расчёта в памяти; масштабируемый импорт и выборка через хранилище должны быть отдельными операциями. Нельзя загружать весь файл на 3 ГБ в дерево Jackson.

## Границы Java-модулей

Предложенные имена DTO/интерфейсов ниже должен реализовать участник 2 в общем `domain/` до независимой интеграции. Java-классы этих контрактов пока не созданы.

| Интерфейс | Вход | Выход / ответственность |
|---|---|---|
| DatasetImporter | InputStream, режим STRICT | Ссылка на сохранённый набор + ValidationReport; потоковый Jackson и пакетная запись |
| DatasetRepository | datasetId, область/типы | Геометрия в метрах, исходные атрибуты, граф existing upstream, подключения и ограничения |
| RoutingService | DatasetContext, RulesCatalog, SearchOptions | Список CandidateNetwork: узлы, ориентированные от врезки рёбра, врезки, подключённые/неподключённые ОКС |
| EngineeringService | DatasetContext, CandidateNetwork, RulesCatalog | EvaluatedVariant: расходы/диаметры, реконструкция, расходы по категориям, score, нарушения |
| RouteValidator | DatasetContext, EvaluatedVariant | Проверка габаритов после назначения ДУ, пересечений, топологии, камер и ограничений |
| ResultExporter | Список прошедших проверку вариантов, OutputStream | Один FeatureCollection по разделу 10, без загрузки результата целиком в память |

CandidateNetwork: рёбра с `id`, `startNodeId`, `endNodeId`, полилинией XY и `layingMethod`; узлы с `id`, XY и типом TIE_IN/CHAMBER/TECHNICAL/CONNECTION; точки врезки с исходным объектом и положением вдоль линии; листья с ID исходного ОКС и точки подключения. Врезка всегда имеет связь с исходным объектом, не просто координату.

Направление новых рёбер: от источника к потребителям. Не путать его с `upstream_object_id` существующих объектов. Для режима 2D depth отсутствует внутри геометрии, при экспорте соответствующие свойства равны null.

EvaluatedVariant содержит исходный CandidateNetwork, рассчитанные атрибуты новых рёбер, интервалы реконструкции с геометрией, камеры и категории стоимости. Каждый шаг возвращает диагностические сообщения с `code`, `message`, `objectIds`, `severity`. Ошибка кандидата не превращается в нулевую цену; кандидат исключается либо перестраивается. Отсутствие маршрута к отдельному ОКС даёт частичный результат со штрафом.

## API

Префикс `/api/v1`. Для статусов/метаданных JSON, для файлов GeoJSON. Ошибки: `{ "code": "...", "message": "...", "details": [] }`. Сервер генерирует ID и имена файлов; не использует имя загрузки как путь на диске.

| Метод | Путь | Назначение | Состояние |
|---|---|---|---|
| GET | `/meta` | Версия каркаса, CRS и доступные возможности | Реализован |
| GET | `/rules` | Общий справочник | Реализован |
| POST | `/datasets` | multipart `file`; сохранить файл на диск, вернуть 202 `{datasetId, status: "VALIDATING"}` | План |
| GET | `/datasets/{id}` | Статус VALIDATING/READY/INVALID/FAILED, статистика, сгруппированные ошибки | План |
| GET | `/datasets/{id}/features?bbox=...&types=...&limit=...&cursor=...` | GeoJSON ограниченной выборки для карты; bbox в EPSG:4326, cursor — следующая страница | План |
| POST | `/jobs` | `{datasetId, mode: "2d", maxVariants: 3}`; 202 `{jobId, status: "QUEUED"}`; невалидный набор — 422 | План |
| GET | `/jobs/{id}` | QUEUED/RUNNING/SUCCEEDED/PARTIAL/FAILED, stage, progress, сообщения, summaries | План |
| GET | `/jobs/{id}/features?variantId=...&bbox=...&limit=...&cursor=...` | Геометрия результата для карты | План |
| GET | `/jobs/{id}/result` | Потоковая выгрузка полного итогового GeoJSON | План |

Для страниц features используем FeatureCollection с дополнительным верхним полем `next_cursor`; это внутренний API. В конкурсном экспорте дополнительных полей пагинации нет. Каждая summary сохраняет точные имена из приложения: `calculated_cost`, `construction_cost`, `chamber_construction_cost`, `tie_in_cost`, `reconstruction_cost`, `chamber_reconstruction_cost`, `unconnected_penalty`, `new_network_length`, `reconstruction_length`, `length`, `score`, `rank`, `unconnected_oks_ids`, `variant_id`, `id`, `object_type`.

Поддержка 50 пользователей не означает запуск 50 расчётов одновременно. Ограниченная очередь и настраиваемое число рабочих потоков; первоначально один тяжёлый расчёт за раз. Валидацию размера и квоты диска проверять до/во время чтения; временные файлы очищать по политике хранения.

## Ограничения и неизвестные значения

Строгий режим обязателен. `flow_tph` отсутствует != `flow_tph=0`. Unknown restriction — ошибка конфигурации, а не свободная территория. Источник, циклы upstream, ссылки и уникальность проверяются до расчёта.

Демонстрационный адаптер старого набора пока не реализован. Если он появится: отдельная опция, исходный файл сохраняется, список всех преобразований и допущений попадает в отчёт. Его результат не маркируется как конкурсно корректный, пока организаторы не подтвердят правила.

## Что считается интеграцией

Frontend сначала может использовать фиксированный синтетический fixture по этому контракту. В общей сборке он получает те же поля из API. Моки обозначаются и отключаются явно; недоступный backend не должен автоматически заменяться красивым фиктивным результатом.

Routing и engineering совместно отвечают за цикл исправлений. Технический узел не должен скрывать превышение длины, разбиение линии не должно менять стоимость без изменения параметров, общие интервалы реконструкции не должны учитываться дважды.
